# 多 Agent 协同设计

> 【结论】
> 1. 你要的是**两套 Agent 体系**，不要混为一谈：**研发期**（AI 帮你写代码/做文档）和**产品内**（App 里服务用户/商家/运营的 Agent）。
> 2. 产品内先做「1 个编排器 + 3 个专业 Agent + 1 个审核 Agent」，跑通再扩；不要一上来做 10 个 Agent 互相聊天。
> 3. 多 Agent 的成本 80% 花在「上下文重复传递」；控制上下文比换便宜模型更有效。
> 4. 本目录附可运行脚手架 `agentflow/`，`python main.py --mock` 零依赖跑通。

---

## 一、两套体系

| | 研发期 Agent | 产品内 Agent |
|---|---|---|
| 用户 | 你/开发同学 | App 的用户、商家、运营 |
| 目标 | 更快写出、改对、测过 | 回答问题、给建议、做审核、出报表 |
| 形态 | IDE/CLI/对话 | API 服务，嵌在后端 |
| 成本 | ¥6–224/月 | ¥0.45/活跃用户/月 |
| 失败代价 | 返工 | 用户投诉/合规事故 |
| 关键 | 提示词、上下文、验收 | 路由、工具、审核、预算 |

## 二、产品内 Agent 的角色划分

```
                    ┌──────────────────────────┐
   用户端请求 ──────►│   Supervisor（编排器）     │
   商家端请求 ──────►│  意图识别 · 路由 · 预算 · 兜底 │
   系统端请求 ──────►└───────┬──────────────────┘
                             │
        ┌────────────┬───────┼────────┬────────────┐
        ▼            ▼       ▼        ▼            ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ 用户助手  │ │ 商家运营  │ │ 数据分析  │ │ 内容审核  │
  │ 找店/推荐 │ │ 活动/文案 │ │ 指标/归因 │ │ 违规/敏感 │
  └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘
       └────────────┴────────────┴────────────┘
                             │
                  ┌──────────▼──────────┐
                  │ 共享层：工具 / 记忆 / 知识库 │
                  │ 检索 · 数据库 · 规则 · 日志 │
                  └─────────────────────┘
```

| Agent | 职责 | 工具 | 不该做什么 |
|---|---|---|---|
| Supervisor | 判断意图、选 Agent、控预算、兜底 | 无（只路由） | 不直接生成业务内容 |
| 用户助手 | 找店、推荐、问答、下单引导 | 搜索、推荐、订单查询 | 不承诺优惠、不改订单 |
| 商家运营 | 活动建议、文案、数据解读 | 商家数据、模板库、日历 | 不碰其他商家数据 |
| 数据分析 | 指标查询、异常归因、周报 | SQL/指标 API、图表 | 不直接改业务数据 |
| 内容审核 | 文本/图片合规、广告法、敏感词 | 审核 API、规则库 | 不做最终处罚（人审兜底） |

**审核 Agent 必须是必经节点**：任何面向用户/商家的生成内容，先过审核再返回。这是合规底线，不是可选项。

## 三、五种编排模式（按需选，不要全上）

| 模式 | 用法 | 例子 | 成本 |
|---|---|---|---|
| 路由（Router） | 一个请求只给一个 Agent | 用户问「附近有什么」→ 用户助手 | 最低 |
| 顺序（Pipeline） | A 的输出给 B | 数据分析 → 商家运营写建议 | 中 |
| 并行（Parallel） | 多 Agent 同时算，汇总 | 同时查订单/库存/评价 | 中高 |
| 反思（Reflection） | 生成 → 审核 → 重写 | 文案生成 → 合规检查 → 改写 | 高 |
| 人在环（HITL） | 高风险动作人工确认 | 退款、封号、批量发券 | 最高 |

【建议】MVP 只用「路由 + 顺序 + 审核」；并行和反思等有明确收益再加。

## 四、消息与状态（开发同学照这个实现）

```json
{
  "trace_id": "t-20261109-001",
  "from": "supervisor",
  "to": "merchant_ops",
  "task": "根据本周数据给商家一条运营建议",
  "context": {"merchant_id": "m_123", "week": "2026-W45"},
  "constraints": {"max_tokens": 4000, "language": "zh", "no_price_promise": true},
  "budget": {"tokens_left": 12000, "steps_left": 4}
}
```

规则：

1. **每个 Agent 只拿自己需要的最小上下文**，不要把全量对话转发给所有 Agent。
2. **工具调用结果要截断**（Top 5 条、500 字以内），否则上下文爆炸。
3. **每个请求带 `trace_id`**，全链路日志可追。
4. **每个 Agent 有 `max_steps`**（建议 3–5），超了就返回「需要人工」。
5. **写操作必须幂等 + 人工确认**，Agent 不直接扣款/封号。

## 五、成本控制（比换模型更有效）

| 手段 | 效果 |
|---|---|
| 路由：简单请求走轻量模型 | 成本降 50–70% |
| 上下文裁剪：只传必要字段 | 成本降 30–50% |
| 结果缓存：相同问题 1 小时内复用 | 成本降 10–30% |
| 工具结果截断 | 避免 10 倍 token |
| 每用户日限额 + 全局熔断 | 防失控 |
| 流式输出 + 超时中断 | 防「用户走了还在烧」 |

## 六、失败与兜底

| 情况 | 处理 |
|---|---|
| 模型超时 | 重试 1 次 → 降级轻量模型 → 返回兜底话术 |
| 工具报错 | 返回「暂时查不到」，不编造数据 |
| 审核不通过 | 返回改写版或「换个说法」；连续 2 次转人工 |
| 超预算 | 停止，返回「今日次数用完」 |
| 意图不明 | 追问 1 次，仍不明转人工/菜单 |

**永远不要让 Agent 编造业务数据**：查不到就说查不到，这比说错强 100 倍。

## 七、评测（上线前必须做）

| 指标 | 目标 |
|---|---|
| 任务成功率 | > 85% |
| 首次响应 P95 | < 3 秒（流式首字 < 1 秒） |
| 单任务成本 | < ¥0.05 |
| 审核拦截准确率 | > 95%（人工抽检 100 条） |
| 幻觉率（编造数据） | 0（业务数据类） |

准备 50 条真实问题做回归集，每次改提示词/换模型都跑一遍。

| 阶段 | 做什么 | 工具 |

| 有明确收益后 | 再考虑并行、反思、多 Agent 协商 | LangGraph |

## 九、脚手架怎么跑

```bash
cd 04_多Agent系统/agentflow
python main.py --mock "帮我看下本周商家数据，给一条运营建议"
```

- `--mock`：不调真实模型，用内置假数据跑通编排、路由、审核、预算、日志。
- 配 `DEEPSEEK_API_KEY` 环境变量后去掉 `--mock`，走 OpenAI 兼容接口。
- 代码零第三方依赖，只用标准库，方便嵌进任何后端。
